# Context Ops —— AI 应用的上下文工程与效果闭环

> **一句话定位**：把「上下文」做成**可观测、可归因、可调优、可验证**的一等公民。
> 不只回答"模型答得对不对"，而是回答"**我该改哪里**"。

**核心结果（本地可复现 · 知识库 24 条 · 用例 15 条）**

| 指标 | ① naive baseline | ② +上下文优化 | ③ +上下文校验器 |
|---|---|---|---|
| **答案准确率** | 0.467 | 0.733 | **0.933** |
| **漏拒率 ↓**（该拒却答了 = 幻觉风险） | **1.000** | **1.000** | **0.000** |
| **过拒率 ↓**（该答却拒了 = 可用性损失） | 0.000 | 0.000 | **0.000** |
| 关键证据入选率 | 0.867 | 1.000 | 1.000 |
| 上下文利用率 ★ | 0.200 | 0.167 | 0.134 |
| 平均输入 token | 228.0 | 288.5 | 288.5 |
| P95 延迟 (ms) | 1.99 | 1.01 | 2.00 |

**两段增益各自可归因**：
- `0.467 → 0.733`（+0.266）：**上下文组装策略**的贡献（去重 + Token 预算 + 首尾优先排列）
- `0.733 → 0.933`（+0.200）：**上下文校验器**的贡献（漏拒率 `1.0 → 0.0`）

> ⚠️ **同时披露变差的指标**：上下文利用率 0.200 → 0.134（选了更多证据，单条被引用的比例被稀释）、
> token 成本 +26.5%（228.0 → 288.5）。
> 这不是"全面变好"，是**拿成本换准确率**——不报喜不报忧，并且已经据此规划了压缩策略。

## 一、它解决什么问题

改 AI 应用时，最难的不是"改"，而是"**不知道该改哪**"：

```
用户问："Milvus 是什么？" → 系统答错了

为什么会错？四种完全不同的原因，现象却一模一样：
  ① 检索没召回          → 该改召回策略
  ② 召回但没进上下文     → 该改组装/预算/去重
  ③ 进了上下文但被忽略   → 该改位置/信噪比
  ④ 上下文都对但答错了   → 该改 prompt/模型

现实中的做法：猜。猜错了就再猜一次。
本项目的做法：用数据定位到具体哪一环。
```

**而"该不该拒答"是第五种，也是最容易被做错的一种**——因为它包含**两类方向相反**的错误：

| 错误 | 现象 | 代价 |
|---|---|---|
| **漏拒**（该拒却答了） | 模型基于无关证据硬答 | **幻觉，代价高** |
| **过拒**（该答却拒了） | 用户什么都拿不到 | 可用性损失 |

把这两类合成一个"准确率"，它们会互相抵消 —— 那等于什么都没说。**必须分开度量。**

## 三、核心设计

### 1. 快照 Schema —— 整个项目的地基

**为什么 Schema 要先定**：归因、评测、优化全都依赖它。**逻辑错了能改，数据没记要全量重跑。**

三个「护城河字段」：

| 字段 | 没有它会怎样 |
|---|---|
| **`dropped[].reason`** | 无法回答"好证据为什么没进上下文"→ ② 类失败查不出来 |
| **`answer.cited_evidence`** | 算不出「上下文利用率」→ ③ 类失败查不出来 |
| **`context.strategy_version`** | 评测结果无法归因到具体策略 → 不同策略无法对比 |

> 补充：`ValidatorResult` 也是在 Schema 里**先留好位置、实现后补**的。
> 这个"先定契约、后填实现"的顺序，让补校验器时没有动过任何已有数据结构。

### 2. 上下文组装器 —— 策略可插拔

两个策略共享同一接口（这是 A/B 对比的前提）：

| 策略 | 做什么 | 为什么这样设计 |
|---|---|---|
| **NaiveTopK** | 直接取检索返回的前 k 条 | 真实朴素实现——**它的缺陷正是要验证的东西** |
| **HeadTailPriority** | 去重 + 预算控制 + 首尾优先排列 | 最相关的放开头和结尾，规避 Lost in the Middle |

**关键**：naive 里**绝不能偷偷排序**（我第一版就这么干了，导致实验失效，见问题档案坑 1）。

### 3. 上下文校验器 —— 决定"能不能答"，且只做这一件事

**核心判断：`rebuild` 与 `refuse` 的分野**

```
证据不够 → 先问一句：是"压根没召回到"，还是"召回到了但被组装砍了"？
              候选集里也没有 → refuse （知识库确实没有，重建也是浪费）
              候选集里有     → rebuild（放宽组装，而**不是**重新检索）
```

这个判断直接复用组装阶段留下的 `dropped[].reason` —— **校验器和归因器共用同一份留痕**。
而且它保证了一件事：**重建永远不会做无用功**（注定救不回来的场景已经被 `refuse` 拦在前面了）。

**冲突裁决的前提：只拒"与问题相关"的冲突**

两条证据互相矛盾，但如果矛盾点**不是问题所问**，不该因此拒绝回答整个问题：

```
问「Milvus 是什么？」           → 上下文里两条证据在"部署依赖"上冲突
                                  → 与问题无关，照常作答 ✓
问「Milvus 部署依赖 MinIO 吗？」 → 同样的冲突，正是问题所问
                                  → 拒答，而不是选择性采信其中一条 ✓
```
（如果在这里不做区分，会把「Milvus 是什么」这种最常规的问题一起误杀——实测中确实踩到了。）

**重建有次数上限**：`max_rebuild=1`。没有上限的重建就是另一种死循环——这和 Agent 运行时里的 `max_steps` 是同一个思想。

**为什么用确定性规则、不调 LLM**：校验结论必须**可靠、可复现、零成本**。LLM 适合做候选召回，不适合做最终裁决——它每次给的答案可能不一样，评测就没法回归。

### 4. 归因器 —— 把失败分到"该改哪一环"

```
① not_retrieved           目标证据不在检索候选里        → 改检索
② retrieved_not_selected  在候选里但被组装砍掉了        → 改预算/去重/排序
      └ 再细分被裁原因：budget_exceeded / duplicate / low_score
③ selected_not_used       进了上下文但模型没用它        → 改位置/信噪比
④ generation_error        上下文没问题但答案还是错       → 改 prompt/模型
⑤ over_refusal            本可回答却拒答                → 改校验阈值（过严）
⑥ missed_refusal          本应拒答却作答                → 改校验阈值（过松）/ 补校验
```

**⑤⑥ 必须排在最前面判定**：拒答是二值动作，两类错误代价反向，
如果混进 `generation_error`，一个"准确率"会把它们抵消掉 —— 等于什么都没说。

**归因用确定性规则（不调 LLM）**：必须可靠、可复现、零成本。

## 四、工程问题档案（本项目最值钱的部分）

五个坑，**前三个是"实验设计"层面的，后两个是"架构与指标"层面的**。

| # | 坑 | 现象 | 根因 | 定位方法 | 修复 |
|---|---|---|---|---|---|
| 1 | **baseline 里偷偷排序** | 两个策略指标完全一样，A/B 失效 | 在 `NaiveTopK.build()` 里写了 `sorted(candidates, key=score)` —— **baseline 自己做了优化**，把要验证的变量抹掉了 | **写诊断脚本打中间变量**（打印每条 position/penalty/relevance/weight），一眼看到"最相关的怎么总在第一位" | 改成真实的 `candidates[:k]`（不重排） |
| 2 | **"打乱顺序"没真的打乱** | 改成交错后还是没差异 | 交错时第一轮迭代就把 `by_relevance[0]`（最高分）放到最前，**等于没打乱** | 同上（继续看中间变量） | 改成实现**真正的 RRF 融合**（`1/(k+rank)` 累加） |
| 3 | **gold 位置"太好"** | 修完前两个坑还是没差异 | 知识库里**每个主题只有 1 条文档** → 目标证据总排前两位 → **落在"中间惩罚区"之外**，没有被惩罚的机会 | 看诊断输出里 gold 的 position | 补充**同主题干扰文档**（真实知识库里同一主题本来就有多条） |
| 4 | **拒答判断藏错了地方** | 校验逻辑无法被单独评测 | 判"该不该答"写在了 `MockGenerator` 里（`max_relevance < FLOOR` 就拒答）——**生成器的职责是"怎么答"，不是"能不能答"**。缠在一起后，校验器的准确率永远测不出来 | 重构时把拒答逻辑抽走做对照实验，**`漏拒率` 立刻从 0 暴露成 1.0** | 抽成独立 `ContextValidator`，在生成之前守门 |
| 5 | **相关性等权平均导致过拒** | 「FastAPI 有什么特点？」被判成"知识库没有相关内容" → 拒答，但证据其实全都正确入选了 | 相关性用了「英文词覆盖率 + 中文字覆盖率」的**等权平均**。而"特点"这种**维度词**在知识库任何文档里都不存在（文档写的是内容，不会写"这是特点"）→ `(1.0 + 0.0)/2 = 0.5`，被拖到阈值以下 | **新加的 `过拒率` 指标**一眼定位（见坑 4：正是因为把它独立出来才测得到） | 改成**加权**：实体词 0.7 / 内容字 0.3 —— 找到"问的对象"比"问的维度"重要得多 |

**坑 4 与坑 5 的因果关系（这个项目最值得讲的一点）**：

> 坑 5 是**被坑 4 的修复暴露出来的**。
> 把校验逻辑从生成器里抽出来之前，它一直藏在"生成错误"这个大类里，看不出方向；
> 一旦独立成模块、有了 `过拒率` / `漏拒率` 两个分开的指标，
> 等权平均的错误**当天就暴露了**。
>
> 一句话总结：**先让模块可测量，问题才会现身。**

**定位方法的共同点**：**不要盯着结果数字猜，把中间变量打出来看。**
坑 1、2 两次盲改都失败，第三次写诊断脚本一次定位；坑 5 靠的是新增的那个指标。

## 五、已知边界与改进方向

| 边界 | 说明 | 改进方向 |
|---|---|---|
| **检索器是字符重叠打分** | 为了让项目零依赖可复现（clone 就能跑），没有引入 embedding | 换成向量检索，接口不变；届时相关性判断也应换成 embedding 相似度 |
| **中文按"字"匹配** | 没装分词器，"单字命中"会带来假阳性 | 接 jieba 做词级匹配，或直接上 embedding |
| **冲突检测规则很粗** | 靠否定词表 + 主题字交集，只能抓"显式矛盾" | 换 NLI 模型做蕴含判断（仍然是确定性推理） |
| **token 成本上升 26.5%** | 校验器放行了更多证据以保准确率 | 加压缩策略（摘要 / 裁剪），按边际收益做更精准的选择 |
| **生成器是 Mock** | 用可控 Mock 隔离了"模型能力"这个变量 | 接真实 LLM 做端到端评测（接口不变） |
| **rebuild 在现有数据上不触发** | 当前 15 条用例里，相关性最高的证据恰好都进了入选集 | 已在 `tests/test_validator.py` 里手工构造场景强制走通这条路 |
| **评测集 15 条偏小** | 覆盖单跳/多跳/库外/冲突 4 类场景，样本量不足以支撑统计结论 | 扩充到 100+ 条，并引入真实 query 日志 |
| **快照存 JSONL** | 单机文件，无查询能力 | 落 Postgres（可 SQL 分析归因分布） |

## 八、技术栈

Python · Pydantic（Schema 校验）· 策略模式（上下文组装可插拔）· 确定性规则归因与校验
（生产化替换：检索换成向量库、生成换成真实 LLM、快照落 Postgres）
