# Context Ops —— AI 应用的上下文工程与效果闭环

> **一句话定位**：把「上下文」做成**可观测、可归因、可调优、可验证**的一等公民。
> 不只回答"模型答得对不对"，而是回答"**我该改哪里**"。

**核心结果（本地可复现）**

| 指标 | naive baseline | HeadTailPriority（优化版） | 变化 |
|---|---|---|---|
| **答案准确率** | 0.714 | **0.929** | **+0.215** |
| 关键证据入选率 | 0.929 | **1.000** | +0.071 |
| 上下文利用率 ★ | 0.171 | 0.143 | −0.028 ⚠️ |
| 平均输入 token | 232.6 | 293.1 | +60.5（+26%）⚠️ |
| P95 延迟 (ms) | 1.03 | 1.01 | −0.02 |

**归因定位**：naive 的 3 条失败**全部是 `selected_not_used`**（证据进了上下文但模型没用它）——
**归因结论与优化方向完全对上**：这正是 HeadTailPriority 要解决的"证据被埋在中间被忽略"问题。

> ⚠️ 注意那两个"变差"的指标：优化提升了准确率，但**牺牲了 token 成本和上下文利用率**。
> 这是真实的工程 trade-off，也是本项目要暴露的东西——**不能只报好消息**。

## 一、它解决什么问题

改 AI 应用时，最难的不是"改"，而是"**不知道该改哪**"：

```
用户问："Milvus 是什么？" → 系统答错了

为什么会错？四种完全不同的原因，现象却一模一样：
  ① 检索没召回          → 该改召回策略
  ② 召回但没进上下文     → 该改组装/预算/去重
  ③ 进了上下文但被忽略   → 该改位置/信噪比
  ④ 上下文都对但答错了   → 该改 prompt/模型

现实中的做法：猜。猜错了就再猜一次。
本项目的做法：用数据定位到具体哪一环。
```

## 三、核心设计

### 1. 快照 Schema —— 整个项目的地基

**为什么 Schema 要先定**：归因、评测、优化全都依赖它。**逻辑错了能改，数据没记要全量重跑。**

三个「护城河字段」：

| 字段 | 没有它会怎样 |
|---|---|
| **`dropped[].reason`** | 无法回答"好证据为什么没进上下文"→ ② 类失败查不出来 |
| **`answer.cited_evidence`** | 算不出「上下文利用率」→ ③ 类失败查不出来 |
| **`context.strategy_version`** | 评测结果无法归因到具体策略 → 不同策略无法对比 |

### 2. 上下文组装器 —— 策略可插拔

两个策略共享同一接口（这是 A/B 对比的前提）：

| 策略 | 做什么 | 为什么这样设计 |
|---|---|---|
| **NaiveTopK** | 直接取检索返回的前 k 条 | 真实朴素实现——**它的缺陷正是要验证的东西** |
| **HeadTailPriority** | 去重 + 预算控制 + 首尾优先排列 | 最相关的放开头和结尾，规避 Lost in the Middle |

**关键**：naive 里**绝不能偷偷排序**（我第一版就这么干了，导致实验失效，见问题档案坑 1）。

### 3. 归因器 —— 把失败分到"该改哪一环"

```
① not_retrieved           目标证据不在检索候选里        → 改检索
② retrieved_not_selected  在候选里但被组装砍掉了        → 改预算/去重/排序
      └ 再细分被裁原因：budget_exceeded / duplicate / low_score
③ selected_not_used       进了上下文但模型没用它        → 改位置/信噪比
④ generation_error        上下文没问题但答案还是错       → 改 prompt/模型
```

**归因用确定性规则（不调 LLM）**：必须可靠、可复现、零成本。

## 四、工程问题档案（本项目最值钱的部分）

三个坑，**全部是"实验设计"层面的**——它们共同说明一件事：**你以为在对比 A 和 B，其实变量被污染了。**

| # | 坑 | 现象 | 根因 | 定位方法 | 修复 |
|---|---|---|---|---|---|
| 1 | **baseline 里偷偷排序** | 两个策略指标完全一样，A/B 失效 | 我在 `NaiveTopK.build()` 里写了 `sorted(candidates, key=score)` —— **baseline 自己做了优化**，把要验证的变量抹掉了 | **写诊断脚本打中间变量**（打印每条的 position/penalty/relevance/weight），一眼看到"最相关的怎么总在第一位" | 改成真实的 `candidates[:k]`（不重排） |
| 2 | **"打乱顺序"没真的打乱** | 改成交错后还是没差异 | 交错时第一轮迭代就把 `by_relevance[0]`（最高分）放到最前，**等于没打乱** | 同上（继续看中间变量） | 改成实现**真正的 RRF 融合**（`1/(k+rank)` 累加），让顺序不再等于相关性序 |
| 3 | **gold 位置"太好"** | 修完前两个坑还是没差异 | 知识库里**每个主题只有 1 条文档** → 目标证据在融合顺序里总排前两位 → **落在"中间惩罚区"之外**，根本没有被惩罚的机会 | 看诊断输出里 gold 的 position | 补充**同主题干扰文档**（真实知识库里同一主题本来就有多条） |

**定位方法的共同点**：**不要盯着结果数字猜，把中间变量打出来看。**
前两次盲改都失败，第三次写诊断脚本一次定位。

## 五、已知边界与改进方向

| 边界 | 说明 | 改进方向 |
|---|---|---|
| **没有 Context Validator** | 目前只有"组装 + 优化"，还没有"证据是否足以作答"的校验与拒答 | 补 Validator（相关性/完整性/冲突）→ 支撑拒答 |
| **token 成本上升 26%** | HeadTail 选了更多证据（6 条 vs 5 条），利用率被稀释 | 加压缩策略（摘要/裁剪），或按边际收益做更精准选择 |
| **Mock 生成器** | 用可控 Mock 隔离了"模型能力"这个变量 | 接真实 LLM 做端到端评测（接口不变） |
| **评测集 14 条偏小** | 覆盖 6 类场景，但样本量不足以支撑统计结论 | 扩充到 100+ 条，并引入真实 query 日志 |
| **快照存 JSONL** | 单机文件，无查询能力 | 落 Postgres（可 SQL 分析归因分布） |

## 六、快速开始

```bash
# 依赖：只需要 pydantic
pip install pydantic

# 跑评测（对两个上下文策略做 A/B 对比 + 归因）
cd context_ops
python eval/run_eval.py

# 诊断脚本（看中间变量：每条证据的位置/惩罚/权重）
python diagnose.py
```

**输出示例**：

```

检索召回率                            1.0           1.0        +0.000
关键证据入选率                        0.929           1.0        +0.071
上下文利用率 ★                       0.171         0.143        -0.028
准确率                            0.714         0.929        +0.215
平均输入 token                     232.6         293.1       +60.500

归因分布 · 策略 [naive]
  correct                      8
  selected_not_used            3      ← 证据进了上下文但没被用（位置问题）
  correct_refusal              2
  retrieved_not_selected       1
```

## 七、目录结构

```
context_ops/
├── schemas.py               ★ 快照 Schema（含 3 个护城河字段）
├── context_builder.py       ★ 上下文组装器（2 个可插拔策略 + 决策留痕）
├── pipeline.py              Pipeline（检索 → 组装 → 生成 → 引用检测 → 快照落库）
├── diagnose.py              诊断脚本（打中间变量，定位实验问题）
├── eval/
│   ├── metrics.py           四层评测指标
│   ├── attribution.py       ★ 失败归因器（四分类 + 被裁原因细分）
│   └── run_eval.py          评测运行器（策略 A/B + 归因报告）
├── data/
│   ├── knowledge_base.jsonl 知识库（含同主题干扰文档）
│   └── eval_cases.jsonl     14 条评测用例
└── snapshots/               每次请求的快照（可回放、可分析）
```

## 八、技术栈

Python · Pydantic（Schema 校验）· 策略模式（上下文组装可插拔）· 确定性规则归因
