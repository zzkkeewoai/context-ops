# Context Ops —— AI 应用的上下文工程与效果闭环

> **一句话定位**：把「上下文」做成**可观测、可归因、可调优、可验证**的一等公民。
> 不只回答"模型答得对不对"，而是回答"**我该改哪里**"。

**核心结果（本地可复现 · 知识库 136 条 · 用例 204 条）**

| 指标 | ① naive baseline | ② +上下文优化 | ③ +上下文校验器 |
|---|---|---|---|
| **答案准确率** | 0.127 | 0.475 | **0.770** |
| **漏拒率 ↓**（该拒却答了 = 幻觉风险） | **1.000** | **1.000** | **0.000** |
| **漏检冲突率 ↓**（证据矛盾却没发现） | **1.000** | **1.000** | **0.059** |
| **过拒率 ↓**（该答却拒了 = 可用性损失） | 0.000 | 0.000 | 0.118 |
| 检索召回率 | 0.961 | 0.961 | 0.961 |
| 关键证据入选率 | 0.544 | 0.951 | 0.951 |
| 上下文利用率 ★ | 0.200 | 0.167 | 0.144 |
| 平均输入 token | 256.9 | 329.3 | 310.3 |
| P95 延迟 (ms) | 4.01 | 5.57 | 5.99 |

**两段增益各自可归因**：
- `0.127 → 0.475`（+0.348）：**上下文组装策略**的贡献（去重 + Token 预算 + 首尾优先排列）
- `0.475 → 0.770`（+0.295）：**上下文校验器**的贡献（漏拒率 `1.0 → 0.000`、漏检冲突率 `1.0 → 0.059`）

> ⚠️ **同时披露变差的指标**：上下文利用率 `0.200 → 0.144`。
> 这不是"全面变好"，是**拿上下文效率换正确性**——不报喜不报忧。

> 📌 **关于指标口径**：这三个"率"的**分母各不相同**，绝不能合成一个：
> 有 gold 的用例看 `过拒率`、库外问题看 `漏拒率`、冲突用例看 `漏检冲突率`。
> 用一个总数当分母是错的（见问题档案坑 7）。

## 一、它解决什么问题

改 AI 应用时，最难的不是"改"，而是"**不知道该改哪**"：

```
用户问："Milvus 是什么？" → 系统答错了

为什么会错？四种完全不同的原因，现象却一模一样：
  ① 检索没召回          → 该改召回策略
  ② 召回但没进上下文     → 该改组装/预算/去重
  ③ 进了上下文但被忽略   → 该改位置/信噪比
  ④ 上下文都对但答错了   → 该改 prompt/模型

现实中的做法：猜。猜错了就再猜一次。
本项目的做法：用数据定位到具体哪一环。
```

**而"该不该拒答"是第五种，也是最容易做错的一种**——它包含**方向相反**的两类错误：

| 错误 | 现象 | 代价 |
|---|---|---|
| **漏拒**（该拒却答了） | 模型基于无关证据硬答 | **幻觉，代价高** |
| **过拒**（该答却拒了） | 用户什么都拿不到 | 可用性损失 |

把这两类合成一个"准确率"，它们会互相抵消 —— 那等于什么都没说。**必须分开度量。**

**第六种是"证据互相矛盾"**：知识库里两份文档对同一件事说法不同。
这类问题的正确处置**既不是照答、也不是一律拒答**（后者是我第一版的做法，
实测过拒率直接飙到 59%），而是**发现它、按来源可信度裁决**。

## 三、核心设计

### 1. 快照 Schema —— 整个项目的地基

**为什么 Schema 要先定**：归因、评测、优化全都依赖它。**逻辑错了能改，数据没记要全量重跑。**

三个「护城河字段」：

| 字段 | 没有它会怎样 |
|---|---|
| **`dropped[].reason`** | 无法回答"好证据为什么没进上下文"→ ② 类失败查不出来 |
| **`answer.cited_evidence`** | 算不出「上下文利用率」→ ③ 类失败查不出来 |
| **`context.strategy_version`** | 评测结果无法归因到具体策略 → 不同策略无法对比 |

> 补充：`ValidatorResult` 也是在 Schema 里**先留好位置、实现后补**的。
> 这个"先定契约、后填实现"的顺序，让补校验器时没有动过任何已有数据结构。

### 2. 上下文组装器 —— 策略可插拔

| 策略 | 做什么 | 为什么这样设计 |
|---|---|---|
| **NaiveTopK** | 直接取检索返回的前 k 条 | 真实朴素实现——**它的缺陷正是要验证的东西** |
| **HeadTailPriority** | 去重 + 预算控制 + 首尾优先排列 | 最相关的放开头和结尾，规避 Lost in the Middle |

**关键**：naive 里**绝不能偷偷排序**（我第一版就这么干了，导致实验失效，见问题档案坑 1）。

### 3. 上下文校验器 —— 决定"能不能答"，且只做这一件事

**核心判断之一：`rebuild` 与 `refuse` 的分野**

```
证据不够 → 先问一句：是"压根没召回到"，还是"召回到了但被组装砍了"？
              候选集里也没有 → refuse （知识库确实没有，重建也是浪费）
              候选集里有     → rebuild（放宽组装，而**不是**重新检索）
```

**核心判断之二：矛盾证据是"裁决"还是"拒答"**

```
检出两条证据互相矛盾
   ├─ 来源可信度差距足够大 → 采信可信的那条，把另一条【剔除上下文】，继续作答
   └─ 分不出高下           → 拒答（不能给一个自己都不确定的结论）
```

为什么必须有这个分支（这是数据集扩大后才逼出来的）：
**"知识库自相矛盾"是数据质量问题，不是"知识库没有内容"**。
第一版只要检出冲突就拒答，在 15 条数据集上看不出问题；
扩到 204 条后过拒率直接飙到 **59%** —— 一半以上的问题答不了，产品上不可用。

另外两个设计细节：
- **冲突检测只对"与问题相关"的冲突生效**：两条证据在"部署依赖"上打架，
  而问题问的是"这是什么" → 照常作答。不做这个区分会把最常规的问题一起误杀。
- **重建有次数上限**（`max_rebuild=1`）：没有上限的重建就是另一种死循环。
- **全部用确定性规则、不调 LLM**：校验结论必须可靠、可复现、零成本，否则评测没法回归。

### 4. 归因器 —— 把失败分到"该改哪一环"

```
① not_retrieved           目标证据不在检索候选里        → 改检索
② retrieved_not_selected  在候选里但被组装砍掉了        → 改预算/去重/排序
      └ 再细分被裁原因：budget_exceeded / duplicate / low_score / validator_reject
③ selected_not_used       进了上下文但模型没用它        → 改位置/信噪比
④ generation_error        上下文没问题但答案还是错       → 改 prompt/模型
⑤ over_refusal            本可回答却拒答                → 改校验阈值（过严）
⑥ missed_refusal          本应拒答却作答                → 改校验规则（过松）
⑦ missed_conflict         证据矛盾却没检出              → 改冲突检测判据
```

**⑤⑥⑦ 必须单独列出来**：它们是方向相反的错误，
如果混进 `generation_error`，一个"准确率"会把它们互相抵消 —— 等于什么都没说。

## 四、数据集：136 篇文档 / 204 条用例是怎么来的

**为什么用脚本生成（`data/build_dataset.py`）而不是手写 JSONL**：

1. **gold 标签必须是"构造时确定"的，不能事后人工补** ——
   204 条用例手工标 gold，一定会出现"标错/漏标/标了自己都忘了为什么"的情况，
   而这种错误**在评测结果里看不出来**，只会让指标莫名其妙地偏低或偏高。
   脚本把"哪条文档是标准答案"变成构造步骤的副产品，从根上消除这类错误。
2. **可复现、可审计**：指标异常时能追回到"是哪个主题的哪条文档"。
3. **不会手抖写错 id / 引用到不存在的文档**（脚本会校验并报错）。

**数据结构**：34 个主题 × 4 篇文档（1 核心 + 2 同主题干扰 + 1 矛盾），每个主题 6 条查询。

| 维度 | 分布 |
|---|---|
| 文档角色 | gold 34 · distractor 68 · conflict 34 |
| 用例类型 | single 58 · multi 78 · out_of_kb 34 · conflict 34 |

三类用例各有各的考点：
- **single / multi**：能不能把对的证据找出来、放进上下文、并被模型用上
- **out_of_kb**：知识库里真的没有时，能不能守住"不知道就说不知道"
- **conflict**：知识库里有互相矛盾的说法时，能不能**发现**它

**关于 `authority`（来源可信度）字段**：
矛盾裁决需要裁决依据。数据集给每篇文档带了 `authority`
（官方文档 0.9 / 参考资料 0.6 / 未经验证的社区内容 0.3）。
**真实系统里这个值不是手写的**，而是从来源类型、更新时间、被引用次数推断或人工标注 ——
这里按角色赋固定值，是为了让数据集自带一个可裁决信号，从而能测出裁决逻辑是否真的生效。

## 五、阈值标定：一个"负结果"，但省下了盲目调参的时间

`calibrate_thresholds.py` 联合扫描了 `MIN_RELEVANCE` × `MIN_TOPIC_OVERLAP` 共 30 组组合：

```
MIN_RELEVANCE  MIN_OVERLAP   准确率   过拒率↓   漏拒率↓   漏检冲突率↓
       0.40        6         0.770    0.118    0.000     0.059   ← 当前取值
       0.35        6         0.770    0.096    0.029     0.059
       0.50        6         0.765    0.154    0.000     0.059
       0.60        6         0.745    0.235    0.000     0.059   ← 最初拍的值
       0.35       12         0.721    0.007    0.029     0.559
       0.60       14         0.672    0.154    0.000     0.676
```

三条结论：

1. **准确率几乎不随阈值变化**（0.672 ~ 0.770）—— 这两个阈值**不是瓶颈**
2. **过拒率与漏检冲突率此消彼长**：`overlap` 从 6 提到 12，
   过拒率 `0.118 → 0.007`（好转），但漏检冲突率 `0.059 → 0.559`（恶化近 10 倍）
3. **没有任何一组参数能同时压住两类错误**

**结论：问题不在参数，在判据本身。**
拿"否定词表 + 字面重叠"去判断"两条文档是否真的矛盾"，
区分不了"真矛盾"和"两条都正常、只是用词不同"——
继续调参只是在两个错误之间来回挪。**下一步该换判据（embedding / NLI），而不是继续调参。**

> 这个负结果的价值：它明确排除了"调参"这条死路，也解释清了指标为什么卡在 0.77。
> **当前取值的理由**：按脚本的筛选标准（过拒≤0.10、漏拒≤0.05、漏检冲突≤0.15），只有 `rel=0.35 / overlap=6` 入选；
> 但我最终仍选 `rel=0.40` —— 因为它的**漏拒率是 0.000**，而 0.35 那一档是 0.029。
> 两者准确率完全相同（0.770），差额全部落在"**宁可拒答、也不给一个错答案**"这一侧：
> 拒答的两类错误代价不对称，**漏拒（幻觉）比过拒（拿不到答案）严重**。

## 六、工程问题档案（本项目最值钱的部分）

八个坑，**每一个都对应一次真实的判断失误**。

### 第一类：实验设计坑（坑 1-3）

| # | 坑 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | **baseline 里偷偷排序** | 两个策略指标完全一样，A/B 失效 | 在 `NaiveTopK.build()` 里写了 `sorted(candidates, key=score)` —— **baseline 自己做了优化**，把要验证的变量抹掉了 | 改成真实的 `candidates[:k]`（不重排） |
| 2 | **"打乱顺序"没真的打乱** | 改成交错后还是没差异 | 交错时第一轮迭代就把 `by_relevance[0]` 放到最前，**等于没打乱** | 改成实现**真正的 RRF 融合**（`1/(k+rank)` 累加） |
| 3 | **gold 位置"太好"** | 修完前两个坑还是没差异 | 知识库里每个主题只有 1 条文档 → 目标证据总排前两位 → **落在"中间惩罚区"之外** | 补充**同主题干扰文档** |

**定位方法的共同点**：**不要盯着结果数字猜，把中间变量打出来看。**
坑 1、2 两次盲改都失败，第三次写诊断脚本一次定位。

### 第二类：架构与指标坑（坑 4-5）

| # | 坑 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 4 | **拒答判断藏错了地方** | 校验逻辑无法被单独评测 | 判"该不该答"写在 `MockGenerator` 里 —— **生成器的职责是"怎么答"，不是"能不能答"** | 抽成独立 `ContextValidator`，在生成之前守门 |
| 5 | **相关性等权平均导致过拒** | 「FastAPI 有什么特点？」被判成"知识库没有相关内容" | "特点"这种**维度词**在任何文档里都不存在（文档写内容，不写"这是特点"）→ `(1.0+0.0)/2 = 0.5` 被拖到阈值下 | 改成**加权**：实体词 0.7 / 内容字 0.3 |

**坑 5 是被坑 4 的修复暴露出来的**：
校验逻辑独立成模块、有了分开的两个指标之后，等权平均的错误当天就现形了。
一句话：**先让模块可测量，问题才会现身。**

### 第三类：数据集扩大后才暴露的坑（坑 6-8）

**这三个坑在小数据集（15 条）上完全看不见 —— 是扩到 204 条之后才炸出来的。**

| # | 坑 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 6 | **冲突一律拒答** | 扩到 204 条后**过拒率飙到 59%**，一半以上问题答不了 | 数据集中每个主题都有一对矛盾文档 → 几乎题题触发"检出冲突就拒答"。**把"数据源有矛盾"这个数据质量问题，用"拒绝回答"来兜底，是过度反应** | 引入来源可信度做**裁决**：分出高下就剔除低可信证据继续作答，分不出才拒答（过拒率 59% → 12.5%） |
| 7 | **指标分母用总数** | `漏拒率 0.412` 一直降不下去 | 把 **conflict 类用例也算进了"该拒答"** —— 但那类用例现在**应该被正常回答**。三类用例的标准完全不同，混在一起算分母是错的 | 三类各用各的分母：有 gold 看**过拒**、库外看**漏拒**、冲突看**漏检冲突** |
| 8 | **阈值调不动** | 怎么调准确率都在 0.65~0.76 之间 | **见第五节**：两个错误此消彼长，没有一组参数能同时压住 | 扫描确认这是**判据**问题而非参数问题，明确下一步换判据 |

**坑 6 与坑 8 的关系**：坑 6 是"设计错了"，坑 8 是"想靠调参补救设计错误，但扫完发现补不了"。
两者合起来说明同一件事：**当两个指标此消彼长、怎么调都压不住时，
就该停下来问"是不是判据选错了"，而不是继续拧参数。**

**为什么小数据集测不出这些**：
15 条用例里只有 1 对矛盾文档，撞不上"冲突大规模触发"；
样本也少到不足以让过拒率、漏检冲突率这些细分指标显现出趋势。
**数据集规模本身就是一种测量能力** —— 这也是为什么我把它从 15 条扩到 204 条。

## 七、已知边界与改进方向

| 边界 | 说明 | 改进方向 |
|---|---|---|
| **冲突判据是字面特征** | 否定词表 + 主题字交集，区分不了"真矛盾"和"用词不同的正常文档"。这是准确率卡在 0.77 的主因 | 换 embedding 相似度 / NLI 蕴含判断（仍是确定性推理，可回归） |
| **检索器是字符重叠打分** | 为了让项目零依赖可复现，没引入 embedding；文档一多，字面重合的噪声就上来了 | 换成向量检索，接口不变；相关性判断也应随之换 |
| **中文按"字"匹配** | 没装分词器，"单字命中"带来假阳性（"问法用词与文档字面不重合"也会被判不相关 → 过拒） | 接 jieba 做词级匹配，或直接上 embedding |
| **`authority` 是数据集给的** | 真实系统里来源可信度需要从来源类型/更新时间/引用次数推断或人工标注 | 接入文档元数据管线自动打分 |
| **生成器是 Mock** | 用可控 Mock 隔离了"模型能力"这个变量 | 接真实 LLM 做端到端评测（接口不变） |
| **过拒率仍有 0.118** | 主要来自"问法用词与文档字面不重合"（如问"片段粒度"而文档写"chunk 大小"） | 同上：换语义判据 |
| **rebuild 在现有数据上不触发** | 当前 204 条里，相关性最高的证据恰好都进了入选集 | 已在 `tests/test_validator.py` 里手工构造场景强制走通这条路 |
| **快照存 JSONL** | 单机文件，无查询能力 | 落 Postgres（可 SQL 分析归因分布） |

## 八、快速开始

```bash
# 依赖：只需要 pydantic
pip install pydantic

cd context_ops

# 1. 单元测试（22 项断言，含强制走通 rebuild 路径）
python tests/test_validator.py

# 2. 重建数据集（从主题定义生成知识库与用例，会自动校验 gold 引用）
python data/build_dataset.py

# 3. 评测：三种配置对比 + 八分类归因
python eval/run_eval.py

# 4. 阈值标定（联合扫描两个阈值，输出两个错误率的交叉曲线）
python calibrate_thresholds.py

# 5. 诊断脚本（逐条打印校验判定与证据顺序）
python diagnose_validator.py
```

## 九、目录结构

```
context_ops/
├── schemas.py               ★ 快照 Schema（护城河字段 + authority + ValidatorResult 契约）
├── context_builder.py       ★ 上下文组装器（2 个可插拔策略 + 决策留痕）
├── context_validator.py     ★ 上下文校验器（相关性/充分性/一致性 → pass·rebuild·refuse + 冲突裁决）
├── pipeline.py              Pipeline（检索 → 组装 → 校验 → 生成 → 引用检测 → 快照落库）
├── calibrate_thresholds.py  ★ 阈值标定（联合扫描两个阈值，看清两个错误率怎么交叉）
├── diagnose.py              诊断脚本（打中间变量，定位实验设计问题）
├── diagnose_validator.py    诊断脚本（逐条打印校验判定）
├── diagnose_over_refusal.py 诊断脚本（统计过拒原因分布，定位是哪条规则拦下的）
├── eval/
│   ├── metrics.py           四层指标（含过拒率 / 漏拒率 / 漏检冲突率，各用各的分母）
│   ├── attribution.py       ★ 失败归因器（八分类 + 被裁原因细分）
│   └── run_eval.py          评测运行器（三配置对比 + 归因报告）
├── tests/
│   └── test_validator.py    22 项断言（含"组装写错时校验器能否兜住"的端到端验证）
├── data/
│   ├── build_dataset.py     ★ 数据集构建脚本（gold 由构造确定 + 格式与引用校验）
│   ├── _gen_a~d.json        主题定义（数据源，34 个主题）
│   ├── knowledge_base.jsonl 知识库 136 条（含 role / topic / authority）
│   └── eval_cases.jsonl     评测用例 204 条（含 category / topic / gold）
└── snapshots/               每次请求的快照（可回放、可分析）
```

## 十、技术栈

Python · Pydantic（Schema 校验）· 策略模式（组装可插拔）· 确定性规则校验与归因
（生产化替换：检索换成向量库、判据换成 embedding/NLI、生成换成真实 LLM、快照落 Postgres）
